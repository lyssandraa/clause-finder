A small local AI model tied hand-written rules at finding contract clauses.

This project looks for six clause types that matter in M&A due diligence and checks every answer against lawyer-reviewed labels. Regex rules and a language model running on one consumer PC scored almost the same, and each was better at different clauses.

This is a first-pass aid, not a reviewer. It misses clauses. A result of "not found" never means a clause is absent, and a lawyer must check every output.

How it works

Both approaches read the same contracts and answer the same question: does this clause exist, and which words are it? Clauses come from the CUAD dataset, 510 public commercial contracts labelled by law students and checked by experienced lawyers.

  Regex rules

The contract is split into sentences. A sentence is returned if it matches a hand-written rule, such as containing "assign" and "without ... consent". The rules were tuned on separate development contracts and then frozen.

  Local language model (Qwen 3 8B)

The model runs on the author's own PC through Ollama, so no contract text leaves the machine. It has five steps, shown below.

  1. Chunk

    Split the contract into pieces of about 20,000 characters, overlapping by 2,000 so a clause on a boundary stays whole.

  2. Ask

    Give the model CUAD's definition of each clause and require exact quotes as JSON, or an empty list.

  3. Verify

    Search for every quote in the contract, allowing only minor differences. Quotes that can't be found are rejected and counted.

  4. Merge

    Map quotes back to their position in the full contract and remove repeats from overlapping chunks.

  5. Show source

    Display the contract's own words, never the model's version of them.

Score 1: is the clause there?

For each contract and clause type, did the tool correctly say whether the clause exists? This matters most in due diligence.

Score 2: is it the right text?

A predicted passage counts only if at least half of the combined words overlap with a lawyer-labelled passage. This is a harsh test, because labels are often fragments of a sentence and a useful answer can still fail it.

    Where it went wrong

    Up to five examples per clause type and approach, most serious first. Some are arguably labelling choices, because annotators don't always agree on where a clause starts and ends.

    These never reached the output. Several are generic boilerplate the contract doesn't contain. Some may be poor copying of real text instead of invention.

    Limitations and legal risks

    Missed clauses are the most dangerous error

    Finding text isn't legal analysis

    The tool doesn't decide whether a deal structure triggers a change-of-control clause, or how a carve-out changes a cap. Those questions need legal judgement and the whole contract.

    Verified text can still be the wrong clause

    The check proves a quote exists in the contract. It doesn't prove the quote is the right clause type. A 90% fuzzy match could also pass over a small but important wording difference, so read each clause in context.

    The sample is small and narrow

    There are 50 test contracts, and only 14 or 15 positives for two clause types, so a gap of a few points may be noise. These are US public-company filings. Accuracy on English-law or private M&A documents is unknown and probably lower.

    One small model was tested

    These results say nothing about larger models. The code also supports Claude through an API, but Claude has not been evaluated here.

    Client confidentiality still applies

    A local model keeps text on the machine running it, but that machine still needs appropriate security. Only public EDGAR contracts were used in this evaluation.
